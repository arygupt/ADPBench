## Kimi GEMV: confirmed RTL bug; synthesis resource blow-up

The frozen submission has SHA-256
`f5eb1885b6e493590d12b0c30bd7e9cc2ef8510a7c23d999d4884849a1591726`.
In its final COMPUTE cycle, `acc[r] <= acc[r] + ...` and
`out_c_reg <= acc[0]` execute on the same edge. Nonblocking assignments read
the old accumulator, so the first output omits the final 16 products.

An offline, direct-RTL diagnostic used the unchanged source, original parameters,
and the harness's timing testbench with two back-to-back all-ones transactions.
Both first outputs were **48**, while all other outputs were **64**. The golden
answer is 64 for every output. This confirms a functional error independent of
synthesis. It is **not a gate-level benchmark score** and does not replace the
original interrupted-scoring record.

A separate single synthesis probe used the pinned Yosys commit `143eb14f9`,
Icarus 13.0, network disabled, two CPUs and a 5 GB memory limit. Yosys converted
the resettable matrix/vector memories into registers and reached about 283,000
intermediate cells. It was killed with signal 9 after 414.1 seconds, during FSM
extraction. The Docker daemon recorded an `oom` event for the same container.
This was a Linux ARM64 local probe, not a claim that the GitHub AMD64 job had
exactly the same timings or termination signal.

The original GitHub job's confirmed termination was its one-hour job limit.
The evaluator currently resynthesizes the same RTL for all six held-out cases,
and the final scoring record is written only after the whole aggregate returns.
Repeated expensive synthesis can therefore consume the job limit before a
record is saved. Recommended follow-up: synthesize once per immutable submission,
reuse that netlist for all cases, and save bounded stage-level failure evidence.
Do not loosen the functional checks, modify this submission, or enlarge model budgets.

Reproduce the direct-RTL counterexample in the pinned, credential-free sandbox:

```sh
python -m scripts.diagnose_kimi --out /output/new-kimi-diagnostic
# Add --synthesis for one bounded, potentially memory-intensive synthesis probe.
```

## GLM HTTP 400: exact provider reason remains unavailable

The first GLM request was rejected; the second was deliberately not sent. The
saved request uses `glm-5.3-flash`, `/zen/go/v1/chat/completions`, `max_tokens=8192`,
`thinking.type=enabled`, `reasoning_effort=low`, and system/user text messages.
The endpoint matches [OpenCode Go documentation](https://opencode.ai/docs/go/).
The model publisher explicitly supports `low`, `high`, and `max`
[reasoning effort](https://huggingface.co/zai-org/GLM-5.3-Flash#note), so blaming
`low` as inherently unsupported is not supported by the available evidence.

An upstream [Unicode-triggered 400 report](https://github.com/anomalyco/opencode/issues/46378)
does not match this request: its message contents are ASCII. The old exception
handler saved only the HTTP status and discarded the response body; the Actions
logs have no upstream error code or message. Thus parameter translation, gateway
validation and an upstream rejection cannot be distinguished from this artifact.
No specific GLM root cause is claimed without that missing evidence.

The runner now saves a bounded, credential-redacted `provider_error.json` in
private artifacts. Provider bodies and headers are not printed or published to
the website. The first rejection still stops further requests with no retry or
fallback. A conclusive live GLM reproduction would require separately approved,
small subscription-only requests; none were made for this investigation.

Follow-up: the separately authorized [September 23 compatibility canary](go-canary-20260923.md)
captured an explicit upstream rejection of the `thinking` field. That current
request provides actionable evidence; it does not recover or replace this old
batch's missing error body, response, or score.
